# Потоки данных

Как информация собирается, где живёт, как переносится и как с ней работаем вместе с Claude. Схема — на канвасе, страница «Передача в MVP», лист «Потоки данных».

## 1. Где что живёт

| Данные | Где | Кто меняет | Как проверяется |
|---|---|---|---|
| **Содержание**: зоны, квесты, задачи, допуски, цепочки, босс, координаты на карте | репо `content/zones/*.json` | Claude по разговору с Денисом | `npm run check` до коммита |
| **Правила**: ставки видов, округление, испытание, слоты, тиры, курс, доля обмена | репо `content/rules.json` | Claude по решению Дениса | `npm run check` и `npm test` |
| **Награды**: список желаний, витрина казны | репо `content/rewards/*.json`, репо приватный | Денис вместе с Claude | проверка: в пуле тира ≥ 3 вещей |
| **Действия**: взял, отметил, отложил, сдал, вернул, сундук, покупка | база, таблица `events` | только сайт, через API | движок `canApply` перед записью |
| **Результаты и доказательства** | заметка и ссылки — в событии сдачи; сами документы — там, где созданы (Claude Docs, Google Drive) | Денис при сдаче | для боя ссылка обязательна |
| **Производное**: статусы, уровень, XP, золото, сундуки, счётчики | нигде не хранится | — | считает движок `derive` |
| **Память для Claude**: что пройдено, что узнали | проект claude.ai, файл пути и летопись глав | Claude при закрытии главы | Денис читает и правит |

Главное правило: у каждого вида данных один дом. На сайте квесты не создаются, в базе уровень не хранится, в репо нет прогресса.

## 2. Шесть циклов

**А. Новая глава или квест.** Разговор с Claude → Claude правит `zone-N.json` → `npm run check` показывает ошибки и прохождение по уровням → правим допуски по отчёту → коммит → Vercel выкатывает → квест появляется на доске.

**Б. Ежедневная игра.** Сайт → `POST /api/events` → движок проверяет действие (`canApply`) → событие пишется в базу → сайт получает новое состояние (`derive`).

**В. Сдача с результатом.** Результат делается в своём инструменте: документ, таблица, запись. В форме сдачи — заметка «что сделал» и ссылки. Для задачи вида «Бой» ссылка-доказательство обязательна, без неё она засчитывается как тренировка.

**Г. Обратная связь Claude.**
- MVP: кнопки «Скопировать статус» (короткий текст) и «Скопировать журнал событий (JSON)» (всё до последней галочки) во вкладке «Персонаж». Вставляешь в чат.
- v2: защищённый адрес `/api/export` с токеном только для чтения. Claude забирает журнал сам.
- v3: MCP-сервер «Путь проводника». Claude читает события и предлагает правки контента пулл-реквестом.

**Д. Калибровка раз в неделю.** Журнал событий → Claude считает метрики эксперимента: активные дни, сданные квесты, внешние события, сундуки. Затем предлагает правки ставок или квестов → цикл А.

**Е. Сохранение в проект.** При закрытии главы Claude собирает летопись сданного и обновляет файл проекта (квест «Сохранить игру»).

## 3. Правила, которые защищают данные

- **ID квеста вечный.** Переименовать можно, переиспользовать нельзя.
- **ID задачи вечный.** У каждой задачи постоянный `id` вида `П.1-a`. События `task_set` ссылаются на него, поэтому задачи можно переставлять. Переиспользовать `id` нельзя, `npm run check` ловит повторы. Старые журналы с номером задачи переводит `upgradeEvents`.
- **Часы задачи фиксируются до взятия квеста.** Поменяли часы у взятого — проверка предупреждает (`validate(content, taken)`; снимки часов на момент взятия начнут приходить из базы на этапе 2).
- **Траты — факт, начисления — пересчёт.** Поменяли ставку — XP и золото за прошлое пересчитались. Покупки и обмены остались суммой из события.
- **Журнал событий только дописывается.** Ошибку исправляет новое событие («отложил», «вернул»), старое не удаляется.

## 4. Что когда строим

| Этап | Сбор | Перенос к Claude | Хранилище |
|---|---|---|---|
| Прототип (сейчас) | в браузере | копировать статус и JSON вручную | localStorage |
| MVP | Supabase, одна таблица `events` | то же + файл JSON по кнопке | Supabase |
| v2 | + загрузка фото и файлов | `/api/export` с токеном | Supabase Storage |
| v3 | + навыки и редкость | MCP-сервер | то же |
